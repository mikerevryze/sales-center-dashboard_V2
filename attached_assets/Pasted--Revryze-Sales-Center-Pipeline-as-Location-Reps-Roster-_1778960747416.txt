## Change 4 — Performance: persistent enrichment cache

Root cause of the slow load: `/api/locations/:locationId/calls` sequentially fetches messages for **every** conversation with a 300ms delay (500 calls × 300ms = 2.5 minutes per location). Fix this with a disk-backed enrichment cache plus parallelization.

### Add `calls-cache.json` persistent store

Create `calls-cache.json` at project root with this schema, keyed by `conversationId`:

```json
{
  "conv_abc123": {
    "messageId": "msg_xyz",
    "duration": 245,
    "status": "completed",
    "userId": "user_123",
    "enrichedAt": "2026-05-16T10:00:00Z"
  }
}
```

On server start, load this into a `Map` named `callEnrichmentCache`. Write to disk every 50 new enrichments AND once at the end of each `/api/locations/:locationId/calls` request that performed any enrichment. Use `fs-extra.writeJson` with `{ spaces: 2 }`.

### Cache-first enrichment flow

In `/api/locations/:locationId/calls`, after building the initial `callObjects` array from `conversations/search`, for each conversation:

1. Look up `callEnrichmentCache.get(conv.id)` first
2. If present AND `enrichedAt` is less than 7 days old → apply cached `{ messageId, duration, status, userId }` directly to the call object, **skip the API call entirely**
3. Otherwise add to a `needsEnrichment` array

### Parallelize the `needsEnrichment` batch with concurrency = 8

Replace the existing `for (let i = 0; i < callObjects.length; i++) { await sleep(300); ... }` loop with this inline helper (do not add npm packages):

```javascript
async function enrichWithConcurrency(items, fn, concurrency = 8) {
  const results = new Array(items.length);
  let cursor = 0;
  await Promise.all(
    Array.from({ length: concurrency }, async () => {
      while (cursor < items.length) {
        const idx = cursor++;
        try { results[idx] = await fn(items[idx], idx); }
        catch (e) { results[idx] = null; }
      }
    })
  );
  return results;
}
```

On 429 from a single conversation, back off 3 seconds and retry once. If it fails again, skip that one and continue — **never let one bad conversation block the whole batch**.

After enrichment completes, write the newly enriched entries into `callEnrichmentCache` and persist to `calls-cache.json`.

### Stale-while-revalidate on the calls endpoint

Replace the current hard 5-minute TTL on the in-memory `callsCache` with stale-while-revalidate:

1. If any cached data exists for the location → return it **immediately**, no matter how old
2. If the cache is older than 5 minutes OR missing → trigger a background refresh that does NOT block the response
3. Track in-flight refreshes in a `Set` (`refreshingLocations`) so two concurrent requests for the same location don't double-fetch

Add `GET /api/refresh-status` that returns `{ refreshing: Array.from(refreshingLocations) }` so the frontend can show a status pill.

### Add cache stats debug endpoint

`GET /api/debug/cache-stats` returns:

```json
{
  "totalCached": 1067,
  "freshCount": 1067,
  "staleCount": 0,
  "oldestEntry": "2026-05-09T...",
  "newestEntry": "2026-05-16T..."
}
```

### Bump oppsCache TTL

Change `oppsCache` TTL from 10 minutes to **30 minutes**. Opportunities change less frequently than calls and the won-opp scan is one of the slower fetches.

## Change 6 — Cap initial conversation fetch at 200; extend in background

In `/api/locations/:locationId/calls`:

1. On the first hit with no `extend` query param, paginate up to **2 pages** (200 calls max) instead of 5 pages (500 max). Return `{ calls, total, hasMore: true|false }`.
2. When `?extend=1` is passed, paginate up to 5 pages as before and merge into the cache.
3. In `app.js`, after the initial `fetchClientData` resolves, kick off a second background `fetch('/api/locations/:locationId/calls?extend=1')` for each client. When it returns, merge the new calls into `appData.calls` (dedupe by `conversationId`) and re-render the affected views.

This brings cold-cache first paint roughly 3× faster while preserving the full 500-call ceiling.
